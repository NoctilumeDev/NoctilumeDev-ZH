# 硅谷中国特色改良版_拖鞋（妥协）版单兵工程法

> **一个人做项目时，压扁组织，保留约束。**
>
> 不照搬大厂流程，也不靠“先写了再说”。
> 目标只有一个：**用最少的协调成本，把一个项目从想法真正推到可运行、可验证、可发布。**

这里的“妥协”，不是向质量妥协，而是向单人资源现实妥协：压缩会议、层级和重复审批，
保留需求、架构、实现、验收、发布与冻结这些不能丢的职责。

本文是单兵工程法的 V1，负责“把系统做出来”。当项目进入多进程、多服务、多中间件和真实
故障环境后，继续使用 [V2：运行诊断与运维验收篇](solo-engineering-runtime-diagnostics.md)，
回答系统坏了从哪查、恢复后究竟证明了什么。

---

## 一、先看最简单的版本

如果只记一条，就记这条：

**产品需求 → 架构设计 → 数据库设计 → 后端 + 粗糙前端 → 前后端跑通 → 测试验收 → 前端美术设计 → 全链路回归 → 发布 → 冻结**

它解决的不是“到底先写前端还是先写后端”，而是：

> **先把问题想清楚，再把事实做出来；先跑通，再做好看。**

---

# 二、完整版施工链

## 1. 产品需求

先回答最朴素的问题：

- 我要做什么？
- 谁来用？
- 用户为什么要用？
- 最核心的流程是什么？
- 这一版做到哪里算结束？

不要一上来就想技术栈。

技术是后面的事。

这一阶段最重要的是把一句：

> “我想做一个商城。”

慢慢变成：

> “用户能注册、浏览商品、下单、支付、查看物流、申请售后；管理员能维护商品、库存和订单。”

需求必须能落到真实动作上。

---

## 2. 范围与边界

需求确定以后，马上划边界。

明确：

- 这一版做什么；
- 这一版不做什么；
- 哪些以后再做；
- 什么叫“完成”。

例如：

```text
本阶段做：
注册 / 登录 / 商品 / 购物车 / 下单 / 支付

本阶段不做：
多商户 / 推荐算法 / 秒杀 / 分库分表
```

这一步非常重要。

个人项目最容易死在：

> “顺手再加一个。”

最后功能越来越多，没有任何一个真正收尾。

---

## 3. 领域模型 / 状态模型

小白不用先背“领域驱动设计”。

先回答几个实际问题：

- 系统里到底有哪些东西？
- 它们之间是什么关系？
- 谁负责保存最终事实？
- 状态会怎么变化？

例如订单：

```text
待支付
  ↓
已支付
  ↓
待发货
  ↓
已发货
  ↓
已完成
```

售后又是另一条状态变化。

先把这些画清楚，再写代码。

否则代码写到一半，很容易出现：

> “这个状态到底应该由谁改？”

---

## 4. 架构设计

现在才开始考虑：

- 前端怎么组织；
- 后端怎么分层；
- 要不要拆服务；
- 哪些同步；
- 哪些异步；
- 哪些东西属于一个模块。

个人项目的架构原则不是“越复杂越专业”。

而是：

> **复杂度必须有理由。**

能单体解决，就不要为了“像大厂”硬拆微服务。

需要拆的时候，再拆。

---

## 5. 数据模型 / 数据库设计

这时候再设计数据库。

不是先看到业务名词就建表，而是根据前面的业务事实落地：

```text
用户
商品
订单
订单项
支付
退款
库存
```

然后考虑：

- 主键；
- 外键；
- 唯一约束；
- 索引；
- 状态字段；
- 金额精度；
- 时间字段；
- 事务边界。

一句话：

> **先知道事实是什么，再决定怎么存。**

---

## 6. API / 事件契约

在正式写大量代码之前，把前后端和服务之间怎么说话定下来。

例如：

```text
POST /api/orders
GET  /api/orders/{id}
POST /api/payments
POST /api/refunds
```

至少写清楚：

- 请求参数；
- 返回结果；
- 错误怎么表达；
- 状态码；
- 幂等要求；
- 哪些字段不能随便改。

这样前端和后端不会写着写着互相追着改。

---

# 三、正式施工：后端 + 粗糙前端一起走

## 7. 后端核心链路

先把真正的业务事实做出来。

例如商城：

```text
创建订单
→ 扣减库存
→ 支付
→ 更新订单
→ 发货
→ 完成
```

先保证：

> **业务真的成立。**

不要在这个阶段花三小时调按钮圆角。

---

## 8. 粗糙但能操作的前端

这一步非常重要。

前端不需要漂亮。

甚至可以是：

```text
[创建订单]

[支付]

[发货]

[退款]
```

只要：

- 能点；
- 能填；
- 能看到结果；
- 能把真实流程走完。

它的作用不是美术。

它是一个**系统探针**。

没有这个东西，你只能证明：

> 后端接口自己调用自己没问题。

有了它，你才能证明：

> 用户真的能从浏览器走完整条链路。

所以不是“先后端，最后才前端”。

而是：

> **后端优先，闭环同步。**

---

## 9. 前后端真实跑通

到了这里，必须真正从浏览器走一遍。

不要只看：

```text
Controller 测试通过
Service 测试通过
前端页面能打开
```

这些都不等于系统跑通。

必须真实验证：

```text
浏览器
→ 前端
→ HTTP
→ 后端
→ 数据库
→ 返回
→ 页面状态变化
```

如果是复杂项目，还要继续看：

```text
MQ
Redis
对象存储
搜索
第三方接口
```

一句话：

> **不要让前端和后端各自“通过”，但合起来不能用。**

---

# 四、测试不是最后补作业

## 10. 自动化测试

基础功能稳定后，把重要行为锁住。

包括：

- 单元测试；
- 接口测试；
- 契约测试；
- E2E；
- 回归测试。

测试不是为了数字好看。

而是为了回答：

> “我改了这里，会不会把昨天已经做好的东西弄坏？”

---

## 11. 边界与故障验收

正常路径通过，只能证明：

> 天气晴朗的时候能跑。

还要测：

```text
重复提交怎么办？
网络断了怎么办？
缓存没了怎么办？
消息重复怎么办？
两个请求同时修改怎么办？
服务重启怎么办？
资源不够怎么办？
```

复杂系统尤其需要明确：

> **什么可以降级，什么绝对不能错。**

例如页面推荐挂了，可以暂时不推荐。

但库存、账务、支付事实不能“差不多”。

---

# 五、现在才轮到前端“变漂亮”

## 12. 前端交互设计

业务已经稳定以后，再认真处理：

- 页面信息层级；
- 操作路径；
- 导航；
- 表单；
- 反馈；
- 空状态；
- 错误状态；
- 加载状态；
- 移动端；
- 可访问性。

先让它**好用**。

---

## 13. 前端美术设计

最后再做：

- 配色；
- 字体；
- 留白；
- 纹理；
- 动效；
- 图标；
- 品牌语言；
- 页面气质。

为什么放最后？

因为如果业务结构还在天天改，前端美术越精致，返工越惨。

先把房子的梁柱立稳。

再刷墙。

---

# 六、最后一轮：别让“美术重构”把业务搞坏

## 14. 全链路回归

前端重构完以后，再完整走一遍：

```text
功能
接口
状态
权限
数据库
异常流程
移动端
浏览器
```

必须确认：

> 视觉变好了，但业务事实没有被改变。

特别是前端重构，很容易出现：

```text
按钮还在
↓
接口参数改了
↓
状态展示错了
↓
异常恢复入口消失了
```

所以最后必须回归。

---

## 15. 发布

发布不是 `git push` 完事。

至少应该有：

- 清晰版本；
- README；
- 运行方式；
- 已知限制；
- 测试结果；
- Release；
- 必要的截图 / Demo / 证据。

别人打开 GitHub 时，应该能知道：

> 这是什么、做到哪了、怎么跑、哪些是真的、哪些以后再做。

---

## 16. 冻结

这是个人开发特别容易缺的一步。

完成以后，要敢于说：

> **这一阶段结束。**

不是永远继续修。

冻结以后：

```text
真实 Bug      → 修
安全问题      → 修
依赖漏洞      → 修
新的大功能    → 下一阶段
突然有灵感    → 记文档，不乱改
```

没有冻结，就没有真正的版本。

---

# 七、文档怎么写？

文档不是最后补。

但也不是要求项目开始前把未来三年的东西全部写完。

核心原则：

> **探索阶段允许边做边写；正式里程碑开始以后，当前阶段文档没写清楚，不开始正式代码。**

## M0：探索阶段

M0 可以：

- 草稿；
- 原型；
- 调研；
- 试技术；
- 改想法；
- 边做边写。

这一阶段的目的就是：

> 把“我好像想做这个”变成“我知道自己要做什么”。

## M1 ～ Mn：正式阶段

每一个正式阶段开始以前，至少写清楚：

```text
这一阶段做什么？
不做什么？
改哪些东西？
哪些东西不能被破坏？
怎么验收？
什么条件下算完成？
```

然后再写代码。

所以不是：

> “必须先写完整本项目所有文档。”

而是：

> **马上要施工的这一层，图纸必须先画完。**

这叫滚动式设计，而不是大瀑布。

---

# 八、Git 怎么用？

Git 不是项目写完以后一次性上传。

而是从一开始就用。

推荐：

```text
需求确定
→ commit

架构确定
→ commit

数据库设计确定
→ commit

第一条业务链跑通
→ commit

测试完成
→ commit

某阶段冻结
→ tag / release
```

Git 的作用不是“备份代码”。

它还是：

- 项目历史；
- 决策记录；
- 回滚点；
- 阶段边界；
- 证据链。

一句话：

> **边做边提交，重要节点可寻址。**

---

# 九、为什么不照搬大厂？

大厂很多流程不是错。

它们解决的是：

```text
几百人协作
跨团队依赖
权限
合规
人员流动
线上事故
责任边界
```

所以需要：

- 产品经理；
- 架构师；
- 前端；
- 后端；
- QA；
- SRE；
- 审批；
- Review；
- RFC；
- 发布流程。

这些流程优化的是：

> **组织风险和多人协作。**

而个人项目只有一个人。

如果原样照搬：

```text
我给自己写需求
↓
我给自己开需求评审
↓
我给自己开架构评审
↓
我给自己提 PR
↓
我 Review 我自己
↓
我批准我自己发布
```

那就开始行为艺术了。

---

# 十、个人开发真正应该做什么？

不是把所有工程纪律一起删掉。

而是：

> **删掉角色，保留职责。**

大厂原来是：

```text
产品经理 → 需求
架构师   → 架构
开发     → 实现
QA       → 验收
运维     → 发布
```

个人版变成：

```text
需求职责 → 文档
架构职责 → 设计
开发职责 → 自己
QA 职责  → 自动化 + 真实运行
发布职责 → Git + CI + Release
项目记忆 → 文档 + Git 历史
```

这就是整套方法最核心的一句话：

# **压扁组织，保留约束。**

# 十一、最终箭头

完整版：

```text
产品需求
→ 范围与边界
→ 领域模型 / 状态模型
→ 架构设计
→ 数据模型 / 数据库设计
→ API / 事件契约
→ 后端核心链路 + 粗糙可操作前端
→ 前后端真实跑通
→ 自动化测试
→ 边界 / 故障验收
→ 前端交互设计
→ 前端美术设计
→ 全链路回归
→ 发布
→ 冻结
```

小白施工版：

```text
产品需求
→ 架构设计
→ 数据库设计
→ 后端 + 粗糙前端
→ 前后端跑通
→ 测试验收
→ 前端美术设计
→ 发布
```

两条平行轨道始终贯穿：

```text
文档同行
Git 留痕
```

# 十二、硅谷中国特色改良版

它不是标准的软件工程教材。

也不是“大厂流程缩水版”。

更不是“想到哪写到哪”。

它只是一个没有团队的开发者，为了同时保住：

- 效率；
- 结构；
- 正确性；
- 可维护性；
- 可验证性；

不得不做出的个人工程折中。

硅谷那套，留下快速反馈和工程自治。

中国大厂那套，留下文档、边界和验收纪律。

把组织层级、会议、重复审批和没有收益的形式主义删掉。

最后剩下：

> **先想清楚，再动手。**
>
> **先跑通，再漂亮。**
>
> **边做边记录，阶段先定义后实现。**
>
> **真实运行比口头完成更重要。**
>
> **一个人，也要给未来的自己留下证据。**

所以，姑且叫它：

# **硅谷中国特色改良版_拖鞋（妥协）版单兵工程法**

穿着拖鞋干活。

但图纸、施工、验收，一个都不能少。
