# 单兵工程公共验证闭环法

> **内部工程做得严谨，不等于外部能够验证它。**
>
> 一个人长期维护项目时，很多知识默认存在于自己的电脑、记忆、脚本和操作习惯里。
> 公开仓库真正需要补上的，是一条陌生人也能进入、机器也能复跑、结果也能定位的验证链。

本文接续[《单兵工程法 V2：运行诊断与运维验收篇》](solo-engineering-runtime-diagnostics.md)：
V2 先在本地固定坐标、保存首败、控制变量并证明恢复与清理；本文再把其中适合公开复跑的结论
交给干净环境、CI、PR 和公共证据入口。两者不互相替代。

公共门禁可以稳定复跑已经选定的声明和机制，却不能用 CI 数量替代反例设计。怎样先从事实所有者和不变量选择代表性机制、再用独立测试与产品视角复核真实实现，见[《对抗性工程验收》导读](adversarial-engineering-validation.md#8-代表性失败机制与独立产品复验)。

## 一、这次问题到底是什么？

常见表象是：

```text
本地测试很多
README 也很长
仓库里还有 CI
→ 看起来应该很可靠
```

但公共验证层可能仍然断开：

- 公开 CI 只安装基础依赖，完整测试实际使用的可选组件没有安装；
- 产品明确要求 Windows，核心测试却在 Linux Runner 上运行；
- 浏览器测试存在，但 CI 没有安装浏览器运行时；
- PR 新提交会触发检查，修改标题、正文或目标分支后却不会重新验证；
- 仓库未来启用 merge queue，必需检查却不监听 `merge_group`；
- 本地跑过完整实验，但外部读者找不到哪些证据可以公开复跑；
- 分支、提交、PR head 和检查结果没有在交付前逐一对齐；
- 主页复制了很多版本状态，过几天就与项目仓库漂移。

这些不是“测试写得不够多”，而是：

> **证据存在，但公共入口、执行条件、触发时机和归属关系没有闭合。**

## 二、为什么个人单兵特别容易遇到？

因为同一个人同时知道：

- 项目应该从哪个目录启动；
- 哪个可选依赖必须手动装；
- 哪些测试只能在 Windows 跑；
- 哪个中间件要提前启动；
- 哪份证据是当前的；
- 哪个失败可以忽略，哪个必须阻断。

这套隐含知识在本人脑中可以工作，却没有进入公共合同。

团队里，这些缺口可能由新人、QA、运维、Review 和发布流程不断追问出来；一个人时，
没有第二个人逼自己解释，于是最容易形成：

```text
内部工程层很厚
公共展示层很薄
```

所以它确实是一类典型的单兵工程 Bug：

> **不是不会做工程，而是太熟悉自己的工程，忘了陌生人并不共享上下文。**

## 三、公共验证的七层合同

### 1. 入口合同

陌生人打开仓库后，应迅速知道：

- 这是什么；
- 当前稳定边界是什么；
- 怎么运行最小示例；
- 公开 CI 在验证什么；
- 完整证据在哪里；
- 哪些能力明确不在公开 Runner 中证明。

README、徽章、文档索引和 Release 是入口，不是装饰。

### 2. 依赖合同

CI 安装的必须是测试真正需要的依赖集合，而不是“主包能安装就行”。

例如：

```text
基础库
≠ 浏览器采集依赖
≠ Windows 命令适配依赖
≠ 完整测试依赖
```

如果完整测试引用可选 extra、浏览器、数据库驱动或平台适配器，公共流程必须显式安装，
否则 CI 失败不是产品失败，而是验证环境未履约。

### 3. 平台合同

Runner 必须符合被验证能力的真实平台边界。

如果项目明确 fail-closed：

```text
Windows 能力只在 Windows 成立
```

那么把同一测试放到 Ubuntu 并期待它通过，不叫跨平台验证，而叫改变测试前提。

正确方式是分层：

- 平台无关门禁放 Linux；
- Windows 核心能力放 Windows；
- 浏览器工作台可以独立选择稳定且高效的平台；
- 真正依赖本机中间件与资源的实验留在本地实验室。

### 4. 触发合同

一个工作流“写在 `.github/workflows` 里”不等于它会在正确时机运行。

GitHub 官方说明：`pull_request` 默认只对 `opened`、`synchronize`、`reopened` 三类活动
运行；如果验证结果还依赖 PR 被编辑后的状态，需要显式加入 `edited`。官方同时要求，
使用 merge queue 且依赖 GitHub Actions 必需检查时，工作流还要监听独立的
`merge_group` 事件，否则队列中的必需检查可能永远不报告。

常用的明确写法：

```yaml
on:
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened, edited]
  merge_group:
    types: [checks_requested]
```

是否保留 `branches` 过滤，取决于仓库原来的 PR 范围。修复触发器时不能顺手改变业务
语义。

### 5. 执行合同

公开 CI 必须从干净环境复现，而不是借用开发机残留：

- 锁文件必须生效；
- Wrapper 必须可用；
- 浏览器必须安装；
- 生成文档必须可重建；
- 需要的服务应显式声明；
- 运行命令应与仓库文档一致；
- 失败必须给出可定位的检查名和日志入口。

### 6. 证据合同

不同证据回答不同问题：

| 层级 | 回答的问题 | 不应该冒充什么 |
| --- | --- | --- |
| 静态门禁 | 格式、类型、架构、依赖和文档是否合规 | 真实业务运行 |
| 托管 Runner | 干净环境能否构建并复跑公开测试 | 本机完整中间件实验 |
| 浏览器验收 | 用户链路、响应式和可访问性是否成立 | 后端故障恢复全貌 |
| 本地实验室 | 多实例、故障、容量和中间件边界是否被真实观察 | 任意机器都能零成本复现 |
| 冻结证据 | 某一版本在明确条件下证明了什么 | 当前所有未来版本仍成立 |

公共验证不是把所有实验硬塞进 GitHub Runner，而是公开说明每一层证明到哪里。

### 7. Git 归属合同

交付前必须对齐：

```text
本地分支
→ 本地 HEAD
→ 远程 head 分支
→ PR head OID
→ PR base
→ 该 OID 上的检查结果
```

“某个 PR 绿过”没有意义；必须确认绿的是这次提交、这个 head、这个 base。

## 四、一次真实修复带来的教训

这轮跨仓库审查暴露出三类不同问题。

### 1. 平台错位

某个核心套件最初放在 Ubuntu 上，但产品能力明确冻结为 Windows。测试没有“偶尔不
兼容”，而是按照设计拒绝在错误平台伪造成功。

修复不是把断言放宽，而是把核心矩阵迁回 Windows，同时保留可以独立运行的 Web
Workbench Linux 门禁。

### 2. 依赖不完整

仅仅换成 Windows 仍不够。完整套件还需要浏览器 extra、Windows 命令 extra 和
Chromium。缺少任意一项，公共环境仍与真实合同不一致。

最终需要：

```text
正确 Runner
+ 完整可选依赖
+ 浏览器运行时
+ 与本地一致的测试命令
```

### 3. 触发器缺口

其他仓库的任务本身可以通过，但 PR 工作流只覆盖默认活动类型，也没有为 merge queue
准备 `merge_group`。这会产生一种危险状态：

```text
旧上下文中的绿灯
≠ 当前 PR 语义下的新验证
```

修复时只补触发事件，不修改任务逻辑、原有分支范围、定时任务或权限，避免把“补公共
合同”变成一次无边界重构。

## 五、三层验证架构

个人项目不需要把所有事情都塞进一条巨大 CI。

### 第一层：快速公共门禁

目标：几分钟内回答“这次提交是否具备继续讨论的资格”。

常见内容：

- 格式与静态检查；
- 单元测试和关键集成测试；
- 类型检查与生产构建；
- 文档、架构和生成物一致性；
- 依赖审计；
- 快速浏览器冒烟。

### 第二层：平台完整门禁

目标：在正确系统与运行时矩阵上回答“核心能力是否真实成立”。

常见内容：

- Windows / Linux 专属能力；
- 多个受支持的 JDK、Node 或 Python 版本；
- 真实浏览器运行时；
- 数据库服务容器；
- 完整但仍适合托管 Runner 的测试集合。

### 第三层：本地实验室与冻结证据

目标：回答“复杂系统在明确资源、故障和中间件条件下究竟证明了什么”。

常见内容：

- 多实例竞争；
- MQ、缓存、搜索和对象存储故障；
- 压测与资源停止线；
- 重启、清理和恢复；
- 浏览器、日志、网络和数据库联合证据；
- 可寻址冻结 Bundle / Report / Release。

三层不是高低贵贱，而是成本与证明范围不同。

## 六、标准施工流程

### 步骤 1：先画验证矩阵

| 能力 | 本地命令 | 公开 Runner | 平台 | 依赖 | 预计耗时 | 证据入口 |
| --- | --- | --- | --- | --- | --- | --- |
| 静态门禁 | 仓库命令 | 是 | 通用 | 基础 | 短 | PR check |
| 核心套件 | 仓库命令 | 是 | 真实平台 | 完整 extra | 中 | PR check |
| 浏览器 | 仓库命令 | 是 / 部分 | 浏览器平台 | Chromium | 中 | 报告 / 截图 |
| Full Lab | 专项脚本 | 否 | 本地冻结环境 | 中间件 Profile | 长 | Evidence / Release |

### 步骤 2：在干净环境复跑

不要只在已有开发环境上运行。至少验证：

- 新虚拟环境或干净依赖目录；
- 锁文件安装；
- 支持版本矩阵；
- 生成物和文档门禁；
- 无隐藏全局依赖。

### 步骤 3：让工作流表达真实边界

- 正确 Runner；
- 完整依赖；
- 明确超时；
- 最小权限；
- 稳定且可识别的 job 名称；
- 不用后置覆盖掩盖旧逻辑；
- 不为了绿灯删除 fail-closed 条件。

### 步骤 4：补全触发契约

逐项确认：

- `push` 需要覆盖哪些分支；
- `pull_request` 需要哪些活动类型；
- 是否需要 `workflow_dispatch`；
- 是否使用 `workflow_call`；
- 是否有 schedule；
- 是否启用或未来可能启用 merge queue；
- 路径过滤会不会让必需检查永远等不到结果。

### 步骤 5：用草稿 PR 触发真实公共链路

本地通过只是前置条件。草稿 PR 还要验证：

- workflow 是否真的被触发；
- job 名称是否符合预期；
- Runner 和依赖安装是否正确；
- 失败日志是否足以定位；
- base/head/commit 是否准确；
- 所有检查结束后状态是否 CLEAN。

### 步骤 6：读取页面，不只读日志

最终验收至少包括：

- PR 页面实际显示哪些检查；
- README 徽章和入口是否有效；
- GitHub Actions 页面能否定位到具体 job；
- 新读者是否能从主页进入验证摘要、Release 或在线 Demo；
- 失败时是否有明确恢复和重试入口。

测试命令成功，不代表公共页面已经可用。

### 步骤 7：冻结并去重

验证信息只保留一个稳定事实源：

- 精确里程碑留在项目 README / Release；
- Profile 主页只写稳定角色和入口；
- 动态测试数由生成基线维护；
- 历史实验留在可寻址证据，不复制到多个文档；
- 同一仓库只保留一套工作流所有权，不用新 YAML 覆盖旧 YAML。

## 七、工作流设计的几个硬规则

### 1. 不把 `pull_request_target` 当作省事版 `pull_request`

它运行在目标仓库上下文，涉及不可信 PR 代码时有更高安全风险。没有明确权限模型时，
优先使用普通 `pull_request` 和只读权限。

### 2. 权限从最小开始

普通构建和测试通常只需要：

```yaml
permissions:
  contents: read
```

需要安全扫描、Pages、Release 或评论时，再为对应 job 增加必要权限。

### 3. 检查名必须稳定

分支保护和 ruleset 依赖检查名。随意改 workflow / job 名称，可能让旧必需检查失去来源，
或让仓库永久等待一个不再生成的状态。

### 4. Path filter 必须与必需检查一起设计

如果一个必需检查因为路径过滤没有触发，PR 可能一直显示“等待状态上报”。需要稳定
聚合检查或明确的 always-run gate，不能只看节省了多少 Runner 时间。

### 5. 平台失败不靠跳过掩盖

如果能力只支持 Windows：

- 把它放到 Windows；
- 或在跨平台 job 中明确只验证平台无关部分；
- 不把核心断言改成无条件 skip 后宣称全绿。

## 八、常见错误

### 错误 1：本地全绿，所以 CI 一定没问题

本地可能拥有全局依赖、缓存、浏览器和中间件；Runner 没有。

### 错误 2：CI 绿，所以产品已经被完整证明

托管 Runner 通常没有你的完整 Full Lab，也不应该伪造多实例和资源边界。

### 错误 3：换 Runner 就算修复完成

平台正确以后，还要检查 extras、浏览器、系统工具、Shell 和文件路径。

### 错误 4：新 commit 会复跑，所以触发器完整

默认 PR 活动类型不包括 `edited`；merge queue 又使用独立 `merge_group`。

### 错误 5：PR 绿过，所以当前 commit 安全

必须核对 PR head OID 与检查运行的 SHA。

### 错误 6：为了统一，把所有仓库复制成同一份 CI

平台、依赖、分支范围和证据边界不同。统一的是审查维度，不是机械复制 YAML。

### 错误 7：先写文档，再修代码

如果根因仍在变化，文档会反复改写。先完成修复和线上复跑，再把真实经验沉淀为方法。

## 九、完成定义

一个公开仓库的验证闭环至少满足：

- [ ] README 说明项目、边界、运行入口和证据入口；
- [ ] 徽章指向真实 workflow 或在线预览；
- [ ] 干净环境可以安装依赖并运行公开命令；
- [ ] 核心测试位于真实支持的平台；
- [ ] 完整测试所需 extras 与浏览器已显式安装；
- [ ] `pull_request` 活动类型符合仓库语义；
- [ ] 使用 merge queue 时，必需工作流监听 `merge_group`；
- [ ] job 名称稳定，权限最小，日志可定位；
- [ ] 本地分支、远程 head、PR head OID 和检查 SHA 一致；
- [ ] 草稿 PR 已真实触发并完成全部线上检查；
- [ ] 本地实验室和公开 Runner 的证明范围被明确区分；
- [ ] 动态状态只有一个事实源，主页没有复制易漂移数字；
- [ ] 修复没有混入无关文件、旧草稿或用户本地证据。

## 十一、最终箭头

```text
内部测试
→ 干净环境复跑
→ 正确平台与完整依赖
→ 完整触发契约
→ 草稿 PR 真实运行
→ base / head / SHA / checks 对齐
→ 公共入口可读
→ 本地证据边界可解释
→ 冻结
```

这套方法最核心的一句话是：

> **不要只让项目在自己手里成立，还要让它在公共证据链上成立。**
