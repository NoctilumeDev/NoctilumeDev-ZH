# 《保护零：从答案生成到事实成立》导读与复核索引

> 正式全文：[20 页 PDF · 论文体工程复盘 · 归档修订版](protecting-zero-from-answer-to-fact.pdf)
>
> 本页只承担站内检索、概念定位和公开证据跳转，不替代 20 页正文。PDF 以作者原始稿为母本，只作少量事实与版面修订，保留原来的章节、公式、表格、附录和叙述节奏。

> **模型可以产生答案，但不能拥有事实。**

## 1. 从“能力怎样产生”到“事实怎样成立”

[《从工具增益到协同复利》](from-tool-gain-to-collaborative-compounding.pdf)讨论的是能力生产：人的问题定义、模型能力、Agent 工作流、有效上下文、历史资产和任务耦合怎样共同改变工程产出。

本文追问另一条轴线：

> 当人的目标定义、模型实现和验收判断都可能带有噪声时，一个工程声明凭什么获得“事实”资格？

“模型生成了什么”与“现实中成立了什么”之间没有天然等号。模型可以写代码、测试、计划和总结，但事实资格必须来自不依赖其自我叙述的观察：数据库最终状态、浏览器 Network 与 DOM、真实进程、Git 对象、发布物字节、远端规则和陌生环境中的复现。

## 2. 为什么“最后由人判断”不是可靠性证明

人不会因为站在流程末端就自动成为 Oracle。最初的目标可能就是人定义错的；审查信息可能不完整；人的介入可能低频、低带宽，而且复核者往往与原始错误前提高度相关。

假设模型当前错误的概率为 `e`，人发现错误的概率为 `d`，发现后正确修复的概率为 `c`，而人把原本正确结果改坏的概率为 `f`。一个简化的复核后错误率可写成：

```text
E_final = e(1 - dc) + (1 - e)f
```

人工介入有净收益，至少要求：

```text
e · d · c > (1 - e) · f
```

这些参数没有在本文中被测量。公式只揭示一个常被忽略的事实：**有人看过**不等于**错误率必然下降**。判断力不是一个原子变量，它至少包含发现、定位、修复、避免误伤、证据独立性和停止能力。

## 3. 错误黏滞态与纠错通道

把系统当前相信的世界简化成两个状态：

- `C`：当前认知仍与现实一致；
- `W`：系统已经进入错误世界。

设 `α` 是从 `C` 进入 `W` 的概率，`β` 是从 `W` 真正返回 `C` 的概率：

```text
P = [[1 - α, α],
     [β, 1 - β]]
```

只要 `β > 0`，`W` 就不是严格数学意义上的吸收态。这里关注的是另一种更常见的风险：共享错误前提会把 `β` 压得很低，使错误状态表现出很强的黏滞性。

当生成者、测试作者和审查者共享同一前提时，后续步骤不是重新观察现实，而是在已经选定的条件空间内继续优化。模型可以高质量实现错误目标，测试可以完整证明实现符合错误合同，审查者也可以诚实确认二者一致。

于是：

```text
W → 实现 W
  → 测试 W
  → 审查 W
  → PASS
  → 仍然 W
```

在这个简化模型中，当 `α + β > 0` 时，稳态分布中的错误态概率为：

```text
π_W = α / (α + β)
```

传统模型优化主要试图降低 `α`。但只要错误率不为零，工程系统还必须提高 `β`：即使已经走错，也要存在回到现实的通道。

数据库、浏览器、Runtime、fresh clone、Release、Git 对象和陌生审查者的共同价值，不是它们“更聪明”，而是它们没有完全继承当前错误叙事，能够为 `W → C` 引入新观测。

## 4. Human-in-the-loop 与独立证据

人的有效纠错概率可以粗略理解为：

```text
β_human ≈ frequency × detection × correction × independence
```

若需求就是这个人自己定义错的，模型照着实现，人再依据原定义复核，那么最后一项可能接近零。此时问题不是人类算力低于 AI，而是纠错通道没有获得新的信息。

所以：

> **Human-in-the-loop 不是可靠性证明。只有 human-with-independent-evidence-in-the-loop 才具有稳定的纠错意义。**

不同审查结构提供的独立性并不相同：

| 审查方式 | 与生成叙事的相关性 | 主要价值 | 主要边界 |
| --- | --- | --- | --- |
| 同模型、同上下文自检 | 极高 | 快速发现表面遗漏 | 容易强化共同前提 |
| 同模型、新上下文 | 较高 | 削弱路径债务 | 仍共享模型先验 |
| 不同模型、同一工件 | 中等 | 增加认知差异 | 仍可能共享语料偏差 |
| 确定性测试 | 较低 | 合同内稳定复算 | 只覆盖已经写出的断言 |
| DB / Browser / Runtime | 更低 | 读取行动后的世界 | 工具本身也可能污染 |
| fresh clone / Release | 更低 | 排除私有路径和本地残留 | 依赖公开资产完整性 |
| 陌生用户或外部环境 | 最低之一 | 引入真实环境方差 | 成本高，仍非绝对真理 |

检查十遍并不意味着十次独立观察。降低验证误差的相关性，往往比增加重复次数更重要。

## 5. 大模型不是纯放大器

若人的有效认知为 `X`，纯放大器可以写成：

```text
Y = aX, a > 1
```

正数被放大为正数，负数被放大为负数，零仍然是零。但大模型同时是生成器，更接近：

```text
Y = aX + ε
```

`ε` 来自训练先验、上下文补全和概率生成。当 `X = 0` 时，输出并不会天然保持为零；模型可能用结构完整、术语正确、语气确定、局部可运行的内容填补空白。

因此必须把两个坐标分开：

```text
T = truth / correctness
C = confidence / coherence
```

最危险的状态不是明显错误，而是：

```text
T 低，C 高
```

真实认知没有增长，可信感却被显著抬高。本文把它称为**伪正数**。

零状态尤其敏感：使用者没有先验，也没有内部反证能力；模型第一次给出的内容可能直接成为新的先验，并在下一轮上下文中被再次强化。

## 6. 保护零

现实存在中间地带；未经约束的生成系统却容易把 `UNKNOWN` 压缩成 `Plausible Completion`。

保护零，就是拒绝让未知在没有证据时被包装成正数。这里必须保留两个彼此关联、但不能合并的轴：

```text
Epistemic state / 命题状态
UNKNOWN
→ UNVERIFIED
→ VERIFIED / REFUTED

Run result / 本轮观察或验收结果
PENDING
→ PASS / FAIL
→ INCONCLUSIVE / BOUNDARY
```

第一个轴回答“这个命题现在知道到什么程度”：

- **UNKNOWN** — 还没有形成可检验声明，或当前信息不足以确定声明内容。允许继续观察、定义问题与边界；不得自动压缩成“看起来可行”。
- **UNVERIFIED** — 已有声明或候选结果，但证据不足。允许继续收集证据并保持未知；不得写成“基本已证实”。
- **VERIFIED** — 在冻结合同和坐标下已有独立证据。允许发布、引用与复算；不等于合同范围之外也正确。
- **REFUTED** — 已有反例或事实冲突。允许修复、收窄并保留现场；不得用新叙事覆盖失败。

第二个轴回答“这一次观察或验收怎样结束”：

- **PENDING** — 计划、执行或资格链仍未闭合。允许继续执行或等待所需证据；不得提前写成 `PASS` 或 `FAIL`。
- **PASS** — 本轮证据满足冻结条件。允许进入该层声明的后续资格步骤；不会自动把命题升级为 `VERIFIED`。
- **FAIL** — 本轮证据与冻结条件冲突。应保留首败、分类并最小修复；不得扩张成合同范围外的全面反驳。
- **INCONCLUSIVE** — 已执行但无法可靠归因。应冻结现场并重新设计实验；不得凭倾向裁决。
- **BOUNDARY** — 位于合同、资源或基础设施边界之外。允许延期并标记 `NOT PROVEN`；不得冒充 `PASS` 或 `FAIL`。

两条轴之间不能机械换算。`PASS` 只有在坐标、合同、证据身份和该层资格门同时成立时，才能支持相应范围内的 `VERIFIED`；`FAIL` 也只能在声明覆盖范围内支持 `REFUTED`。`INCONCLUSIVE` 与 `BOUNDARY` 说明为什么本轮不能支持更强结论，它们不是命题本身的认知状态。

一个可信系统最基础的能力，不是永远给答案，而是在证据尚未到来时维持“不知道”。

## 7. 从原则到可执行方法

[《对抗性工程验收》](adversarial-engineering-validation.pdf)把保护零落成九层事实链：Source、Build、Runtime、Browser、Failure、Artifact、Governance、Cleanup 和 Public Readability。

本轮实际出现的状态转换包括：

- VeriTrail 用预注册的 `3500 MiB` 低内存夹具证明触及停止线时不会制造浏览器证据；正常宿主条件下的正向运行通过。这个对照只证明停止语义，不构成真实宿主低水位与恢复的容量证据；
- VeriTrail 的 `catalog-serve` 拒绝自己 producer 生成的失效物理绑定，修复发生在 producer 而不是 verifier；
- DarkRoomLibrary 的 403 最终由 Network 响应定位为合同外 Origin，产品没有为了迎合验收工具而放宽 CORS；
- PlainJournal 的 16 GiB Core Smoke 保持 `INCONCLUSIVE / HOST CAPACITY BOUNDARY`，32 GiB 验证被单独延期；
- MiniSpringBoot 的 hardening 候选已经形成提交，但没有因为完成度和沉没成本获得整体进入教学主线的权利；其中独立成立的声明修正只在另行裁决后进入主线。

这些案例没有证明系统永不犯错。它们证明的是：红灯能够被保留，边界能够阻止错误升级，新的事实能够推翻原解释。

## 8. 概率性认知与确定性事实之间的两层约束

一个更现实的 AI 工程结构不是寻找“绝不幻觉的神经网络”，而是让不同机制负责不同问题：

```text
AI / LLM
开放世界理解、规划、生成
        ↓ intention / action

Execution layer
Capability / Isolation / Resource
State / Context / Provenance / Recovery
        ↓ runtime facts

Acceptance layer
API / DB / Browser / Git / Release
PASS / FAIL / INCONCLUSIVE / BOUNDARY / PENDING
```

底层执行系统回答“AI 实际做了什么、能接触什么、修改了什么”；上层验收系统回答“行动后的世界究竟变成了什么”。两层共同削弱模型自报结果的裁决权。

它们仍然不能保证真理：确定性程序可以稳定地错，验证器也可能读取错误实例。目标不是消灭不确定性，而是把声明、行动和事实拆成不同类型，并允许交叉读回。

## 9. 它不能改变 Transformer 的理论复杂度

标准 full attention 对输入长度 `n` 的配对规模仍大致随 `O(n²)` 增长。执行系统不能把该算法复杂度直接改成 `O(n)`；改变渐进复杂度需要模型与算法层面的方案。

它能做的是降低有效工作集：

```text
C_effective << C_history
```

Git object、决策记录、运行状态、工件图、测试结果、已知不变量和失败历史如果成为结构化外部状态，模型就不必在每次行动前重新阅读自己的全部对话人生。

这能减少上下文成本和路径债务，但不是“根治幻觉”或“解决注意力平方复杂度”。边界必须保留。

## 10. 单机闭环与社区方差

单机可以证明真实进程、数据库、消息链路、发布物、故障恢复和同宿主多实例语义；它不能冒充跨节点、跨可用区或互联网规模高可用。

PlainJournal 把这条边界测得很具体：16 GiB 宿主已经触及停止线，未来 32 GiB 可以继续代表三实例、容量阶梯和故障恢复，但同一台机器上的三实例仍不是跨机 HA。

个人阶段真正需要闭环的是：

- 核心抽象；
- 最小可信实现；
- 稳定接口；
- reference implementation；
- 可执行验收合同；
- 明确的 NOT PROVEN。

社区最终贡献的不只是更多代码，而是作者无法独自拥有的环境方差：不同架构、操作系统、网络、负载、模型、故障域和长期运行时间。

## 11. 对 FlowKernel 的反向约束

[FlowKernel](https://github.com/NoctilumeDev/FlowKernel) 当前仍是 `Planned`，实现尚未开始。本文不能把理念写成内核能力，但可以为未来研究补充几条设计约束：

1. AI 建议默认属于 `UNVERIFIED proposal`，不能直接成为安全不变量；
2. Fast Path 的权限、硬资源上限和回退必须由确定性机制执行；
3. 调度决策需要持久 provenance，能够说明输入状态、提案、Guard 裁决和实际动作；
4. 执行层记录 action，不替验收层宣告业务事实；
5. 失败恢复必须保留 `UNKNOWN / BOUNDARY`，不能在观测不足时补出成功叙事；
6. 多节点、高并发与长期稳定性必须由未来真实环境证明，路线图不能代替证据。

这是一组需要以后实现和反证的研究输入，不是对 FlowKernel 已完成能力的追加声明。

## 12. 局限

- 本文来自一名使用者的纵向工程实践，不是随机对照实验；
- `α`、`β`、`d`、`c`、`f` 与独立性没有被大样本估计；
- 两状态模型压缩了未知、部分正确、冲突证据与资源中止；
- 外部事实源也会错：浏览器控制层会污染输入，数据库可能指向错误实例，Release 可能与 tag 漂移；
- 保护零会增加延迟与拒绝率，在低风险、一次性创作任务中，过强 fail-closed 未必经济；
- 本文没有解决 AGI，也没有证明某种 AI Execution OS 必然成功。

## 13. 结论

真正成熟的系统不幻想永远不进入错误态，而是让错误态无法长期稳定存在。它既降低 `α`，也提高 `β`；既追求更强模型，也建设错误状态逃逸通道。

大模型带有生成项，因此零不是安全中性点。人在不知道时，模型可能迅速填充空白，并把低真值包装成高可信感。可信系统必须保护零，让 `UNKNOWN` 保持 `UNKNOWN`；只有证据到来以后，才允许声明转为 `VERIFIED`。

未来路线也不是把智能改造成一个永远正确的函数。更可行的是让概率性认知负责开放世界理解，让确定性系统约束行动，让持久状态保存可恢复事实，让外部验证器裁决声明是否成立。

> **模型可以产生答案，但不能拥有事实；智能无法被彻底函数化，但它的产出在成为事实以前，可以接受函数式约束。**
