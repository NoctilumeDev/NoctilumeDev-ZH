# 单兵工程法 V2：运行诊断与运维验收篇

> **把系统做出来以后，还要知道它为什么能跑、坏了从哪查、恢复后究竟证明了什么。**
>
> 排错的目标不只是“把它弄好”，而是尽量保住“为什么变好”这条因果链。

本文是[《硅谷中国特色改良版_拖鞋（妥协）版单兵工程法》](solo-engineering-method.md)
的运行与诊断续篇。

- V1 负责把项目从需求推进到可运行、可验证、可发布；
- V2 负责系统进入真实运行以后，怎样建立诊断基线、保存现场、控制变量、恢复并验收；
- [《单机工程环境全景认知法》](single-machine-engineering-environment.md)负责开工前的机器事实图；
- [《单兵工程公共验证闭环法》](public-verification-loop.md)负责把本地已经成立的事实交给干净环境、CI 和公共页面重新证明。

它不是命令大全，也不承诺靠一张清单消灭所有故障。它提供的是一条有限的诊断闭环：

```text
固定坐标与基线
→ 保存首败现场
→ 分层定位
→ 单变量实验
→ 验证恢复与清理
→ 只声明证据真正支持的结论
```

---

## 一、为什么 V1 以后还需要 V2？

V1 已经要求：

```text
浏览器
→ 前端
→ HTTP
→ 后端
→ 数据库 / 缓存 / MQ / 对象存储
→ 返回
→ 页面状态变化
```

但“完整链路曾经跑通”和“故障发生时能够解释”是两种能力。

> **V1 用浏览器证明系统真的连起来了；V2 从浏览器开始，学习系统坏掉以后应该往哪一层继续追。**

单体、小型全栈和分布式项目都会遇到：

- 页面报错，但后端其实没有收到请求；
- 端口在监听，但应用尚未就绪；
- 代理进程存在，但 DNS、上游线路或 TLS 失败；
- 测试偶发失败，其实是上一轮进程、端口或临时数据没有清理；
- JVM 内存升高，但无法证明是泄漏、缓存增长、负载变化还是采集器开销；
- 消息、回调或定时任务迟到，用旧状态覆盖了新事实；
- 重启以后恢复，却没有解释此前为什么失败；
- 验收工具为了“检查”顺手修改了源码或运行环境。

这些问题的共同点不是“缺少某条命令”，而是：

> **观察、因果、资源所有权和结论边界没有闭合。**

---

## 二、F12 是入口，不是终点

粗糙前端仍然是最早、最便宜的系统探针。页面异常时先看浏览器开发者工具：

```text
Console
Network
Application / Storage
WebSocket / EventStream
请求与响应头
状态码、耗时和重定向
```

它能回答：

- 用户动作是否真的触发了请求；
- 请求发往哪个 origin、路径和方法；
- token、cookie、CORS、缓存和重定向表现如何；
- 响应是否到达浏览器；
- 页面状态是否正确消费了响应。

但浏览器通常不能单独回答：

- DNS、系统代理、容器网络和服务发现到底在哪一层失败；
- 后端线程是在计算、等待锁、等待连接池，还是已经死锁；
- 中间件事实是否已经提交，而响应在返回途中丢失；
- 当前进程、JAR、容器镜像是否真的来自声称的源码状态；
- 重启后恢复是否意味着根因已经消失。

所以：

> **页面报错时先看浏览器；浏览器解释不了，就沿 HTTP、应用、运行时、操作系统、
> 中间件和宿主机逐层向下查。**

## 三、先分清“看到什么”和“能够证明什么”

诊断记录至少区分四类信息：

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| `OBSERVED` | 当前工具直接观察到的事实 | 某时刻端口正在监听、请求返回 502 |
| `CONTROL` | 为区分假设而设置的对照 | 同一请求直连成功、经代理失败 |
| `INFERRED` | 由多项事实支持、仍可能被反例推翻 | 故障更可能位于代理上游而不是应用 |
| `UNKNOWN` | 现有证据不足以判断 | 请求超时后，服务端事务是否已提交 |

不要把下面这些句子直接画等号：

```text
内存高                  ≠ 内存泄漏
线程多                  ≠ 线程泄漏
进程存在                ≠ 服务就绪
端口连接失败            ≠ 端口可安全占用
DNS 解析成功            ≠ HTTP 链路成立
HTTP 超时               ≠ 服务端没有执行
缓存命中                ≠ 命中了调用者要求的事实源
测试后来通过            ≠ 解释了此前失败
重启后恢复              ≠ 根因已找到
Git HEAD 写进报告       ≠ 执行构件来自该 HEAD
```

一个诚实的 `UNKNOWN`，比一个方便但虚构的根因更有价值。

以后无论检查 DNS、HTTP、代理、进程、线程、内存、端口、JVM 还是中间件，都可以先写同一组
五格，而不是先堆命令：

```text
观察：
看到了什么？

允许结论：
这项观察最多能证明什么？

禁止结论：
它不能顺手推出什么？

下一变量：
接下来只改变什么来区分候选原因？

恢复证明：
怎样确认能力恢复、状态正确且现场已经清理？
```

命令是取得观察的工具；五格决定这些观察有没有资格进入结论。

## 四、建立运行时诊断坐标

在复现、压测或故障注入前，先固定“这一次究竟在测什么”：

### 1. 源码与构件

- 仓库、分支、commit、worktree 和未提交状态；
- 实际执行的 JAR、镜像、静态资源或安装包身份；
- 构建来源和构件摘要；
- 是否存在 editable install、旧构件、旧容器或路径指向其他工作树。

`source SHA`、`artifact digest` 和“发生过一次构建”是三种事实。只有在同一条构建链上绑定，
才能支持“这个构件来自这份源码”。

### 2. 运行拓扑

- 哪些进程、容器和中间件本轮应该存在；
- 谁启动它们，谁有资格停止它们；
- 服务、端口、依赖和健康检查的对应关系；
- 单实例、多实例、代理、VPN、Docker、WSL 和宿主机之间的边界。

### 3. 配置与凭据边界

- 生效的 profile、配置文件和关键开关；
- 超时、重试、并发、TTL 和资源限制；
- 凭据只记录存在性、来源类别和权限范围，不把秘密写入日志或证据；
- 临时测试配置必须在结束后恢复，并确认没有污染其他验收者。

### 4. 时间与资源基线

- 开始时间、时区和关键事件时间线；
- 可用内存、磁盘、CPU 和句柄余量；
- 进程、线程、端口、连接和容器起点；
- 启动线、升压线和停止线。

没有坐标时，一次绿色结果很可能只是：

> **某个未知版本，在某个未知环境里，偶然成功了一次。**

## 五、七层诊断栈

不要同时乱查所有层。先根据首个可重复断点，把问题缩到最小层级。

| 层 | 先问什么 | 常见证据 | 不能直接推出 |
| --- | --- | --- | --- |
| 浏览器 | 动作是否触发？请求和状态怎样变化？ | Console、Network、Storage、截图 | 后端一定没执行 |
| HTTP / 网络 | 名称、路由、代理、TLS、连接和响应哪一步失败？ | DNS、直连/代理对照、握手、状态码、耗时 | 超时就是应用 bug |
| 应用 | 请求是否到达？卡在哪个责任边界？ | 结构化日志、request/trace ID、readiness、连接池 | 有日志就是成功提交 |
| Runtime | 线程、堆、GC、锁和句柄如何变化？ | thread dump、heap/GC 序列、运行时指标 | 单次高值就是泄漏 |
| OS | 谁拥有进程、端口、socket、文件和资源？ | PID、父子进程、监听、句柄、事件日志 | 名字相同就是本轮进程 |
| 中间件 | 当前事实、队列、缓存和租约由谁拥有？ | DB、Redis、MQ、注册中心、对象存储事实 | 投影或缓存等于 owner 事实 |
| 宿主与容器 | Windows/Linux、Docker/WSL、文件系统和网络边界怎样？ | daemon、容器、卷、路由、文件系统事实 | 宿主故障等于项目回归 |

复杂问题可能跨层，但诊断动作仍应串行：

```text
确定最外层可观察断点
→ 找到上一层成功事实
→ 找到下一层失败或未知事实
→ 只改变夹在两者之间的一个变量
```

## 六、标准诊断流程

### 步骤 0：先看是否触发停止线

以下情况优先停下升压和新实验：

- 可用内存、磁盘或句柄接近硬线；
- 持续交换、长时间 GC 或系统失去响应；
- 网络、代理、Docker 或文件系统出现新的平台级异常；
- 数据库、库存、账务、支付等硬性事实出现不一致；
- 实验工具开始改变未授权的源码、配置或外部进程；
- 无法确认即将停止、删除或覆盖的对象是否属于本轮。

停止实验不等于产品失败。它首先说明当前运行条件不再有资格支持无条件结论。

### 步骤 1：保存首败

至少保存：

- 精确时间和用户动作；
- 第一个错误，而不是最后一屏连锁报错；
- 浏览器请求、状态码和控制台；
- 对应服务日志和 trace/request ID；
- 进程、端口、连接与资源快照；
- 中间件中已经成立的业务事实；
- 本轮源码、构件、配置和拓扑坐标。

不要先重启、清缓存、杀进程、改代理、拉长 timeout，再回头猜刚才发生了什么。

### 步骤 2：写候选原因，不写结论

例如一次 HTTP 超时可以先列为：

```text
H1 服务未监听或尚未就绪
H2 DNS / 路由 / 代理 / TLS 失败
H3 工作线程、连接池或下游阻塞
H4 服务端已提交，响应在途中丢失
H5 验收工具的资源或超时窗口不足
```

候选原因之间要能由实验区分。无法区分的“可能什么都有问题”不是有效假设。

### 步骤 3：设计最小控制变量

一次只改变一个主要变量，其余尽量固定：

- 直连与代理；
- 单实例与多实例；
- 缓存关闭与开启；
- 同一构件、同一负载下的不同资源档；
- 同一请求在主库事实与投影事实上的表现；
- 同一故障注入前后的请求链。

记录正对照、负对照和预期结果。若实验工具改变了业务原本的锁、事务、资源或时序拓扑，
它测到的可能已经不是原问题。

### 步骤 4：运行并记录时间线

记录事件的先后，而不只保存最终状态：

```text
T0 请求/任务开始
T1 观察到旧状态或取得 lease
T2 新状态提交或 owner 发生变化
T3 旧 actor 恢复
T4 写入被接受、拒绝或结果未知
```

对并发、缓存、MQ、租约和补偿问题，时间线通常比一份最终日志更有解释力。

### 步骤 5：给结论划边界

一次实验可以得到：

- 某候选原因被正反对照支持；
- 某候选原因被反证排除；
- 故障恢复，但根因仍未知；
- 工具或环境污染了实验，结果不可归因；
- 证据不足，需要下一次有界实验。

不要为了写一句漂亮的 RCA，把 `UNKNOWN` 强行压成“已定位”。

### 步骤 6：恢复与清理

按所有权逆序处理：

- 只停止本轮启动且身份已确认的进程、容器和监听者；
- 恢复临时 TTL、代理、路由、环境变量和 profile；
- 清理本轮临时文件、测试数据、连接和浏览器状态；
- 证明端口、线程、进程和 staging 回到预期基线；
- 不删除未知 owner 的数据，不用强制覆盖掩盖状态冲突。

### 步骤 7：重新验收

恢复成功至少分三层：

```text
控制面：服务/daemon/容器报告正常
数据面：真实请求或真实容器可以工作
业务面：代表性用户链路和硬性事实成立
```

只看到进程重新出现，不能算完整恢复。

## 七、常见专题怎样避免误判

### 1. 内存与“泄漏”

一次 RSS 或 heap 高点只能证明当时占用较高。要支持“泄漏”，至少需要在可比较负载下观察：

- 多轮执行后的基线是否持续抬升；
- GC 后存活对象是否持续增长；
- 哪类对象、缓存、队列或 native allocation 保留；
- 观察工具本身占用了多少资源；
- 停止流量、等待回收后是否仍不下降。

压力过大、缓存预热、JIT、文件映射、浏览器多进程和 Docker/WSL 都可能改变表面内存。

### 2. 线程、任务和锁

线程数高不等于线程泄漏。先区分：

- 固定线程池与临时线程；
- 活跃、等待、阻塞和死锁；
- 队列增长与线程增长；
- 调度任务是否重复注册；
- shutdown 后线程是否按合同退出。

至少保留多个时点的 thread dump，单张快照很难解释增长趋势。

### 3. 进程与端口

必须回答：

- PID、父进程、启动时间和可执行路径是谁；
- 监听者是否属于本轮；
- 端口“连不上”是未监听、backlog 拥塞、协议不符还是防火墙拒绝；
- 预检与真正 bind 之间是否存在竞争窗口；
- 测试结束后端口是否真的释放。

不能因为某个进程妨碍测试，就默认拥有终止它的权力。

### 4. DNS、代理与 HTTP

推荐按层对照：

```text
本地监听
→ 名称解析
→ 目标直连
→ 显式代理
→ TLS / HTTP
→ 应用状态码和响应
→ Docker / WSL / VPN 路径
```

显式代理能成功、命令行直连失败，首先证明两条连接路径不同；它不会自动证明应用、DNS、
系统代理或 Git 配置中的哪一个“坏了”。具体 Windows 网络边界见 PlainJournal 的
[《本地开发网络与 Windows 故障边界》](https://github.com/NoctilumeDev/PlainJournal/blob/main/docs/07-local-development-network.md)。

### 5. readiness 与异步成熟度

进程已启动、端口已监听、健康检查为绿，可能仍不表示：

- 依赖连接已经完成；
- MQ consumer 已订阅并可处理业务消息；
- 缓存和索引已经具备代表性数据；
- 定时任务、leader 或 lease 已取得；
- 浏览器需要的静态资源已经可用。

把“进程存活”“服务就绪”“业务成熟”分开验收。

### 6. Docker、WSL 与宿主机

宿主不是透明背景。Windows、Linux、文件系统、虚拟化、容器网络和安全过滤栈都可能产生
不同故障形状。

恢复 Docker 时应先保护代码与容器数据，分清宿主故障和项目失败，再做最小隔离。一个真实案例见
[《Docker Desktop Windows 套接字崩溃：无损恢复与停止边界》](docker-desktop-windows-socket-recovery.md)。

## 八、分布式系统还要检查“当前资格”

幂等回答的是：

> 同一个动作重复执行，副作用会不会重复？

它不自动回答：

> 这个动作现在还有没有资格执行？

需要专门检查：

- 旧请求、旧回调或旧导航能否清除新会话；
- timeout、补偿和定时任务提交前是否重新确认前提；
- lease 过期后的旧 worker 能否继续写；
- 旧事件能否让状态机从新状态回退；
- cache loader 是否会在 invalidation 之后迟到写回旧值；
- 较弱缓存或副本是否越权回答调用者明确要求的强事实；
- cleanup 是否可能删除新世代建立的对象。

一个通用问题是：

```text
Actor 当时观察了什么？
它因此取得了什么有限资格？
提交前世界发生了什么变化？
它是否重新确认资格仍然成立？
若已失权，系统怎样拒绝它？
```

常见保护包括条件更新、版本号、generation、fence、当前 owner 复核和受保护的状态转换。
不要因为某个 actor 曾经持有锁、token、lease 或旧状态，就默认它永远拥有未来的写权限。

对于响应丢失：

> **UNKNOWN 不能冒充失败，也不能冒充成功。**

是否可以安全重试、查询既有结果或必须重新认证，取决于当前还能证明什么，而不是取决于
“无感体验”是否更漂亮。

## 九、测试和验收工具也会污染现场

验收工具不是天然的只读观察者。

典型污染包括：

- `lint` 名义上检查，实际自动格式化源码；
- debugger 或数据库锁改变了原本的事务和线程交错；
- 两套浏览器或测试进程并行运行，改变资源拓扑；
- 临时短 TTL、代理、账户和 feature flag 泄漏到下一项验收；
- 测试 server 缺少真实 API，却把环境缺口报告成产品回归；
- editable install、PATH 或旧 JAR 让测试运行了另一份源码；
- 为了让 CI 变绿，扩大 timeout 或跳过失败，而没有解释首败。

因此每个 verifier 都应先被问：

```text
它声明只读还是允许变换？
它会创建哪些进程、端口、文件和数据？
它怎样证明执行的是当前对象？
它的资源开销会不会改变被测现象？
失败后是否仍会执行清理？
```

对声明只读的检查，执行前后受保护源码发生变化，本轮证据就不能继续支持原源码的正常 PASS。
变化本身仍应保留为“工具污染现场”的证据，而不是被删除。

## 十、运维验收不是“能重新启动”

一次修复或恢复至少回答：

1. **恢复了什么能力？** 是 daemon、接口、真实容器，还是完整业务链？
2. **哪一个变量导致变化？** 若同时升级、清理、重启和改配置，就不能准确归因。
3. **保护了什么数据？** 代码、数据库、卷、对象存储和未提交现场是否安全？
4. **有没有残留？** 进程、端口、线程、连接、临时文件和测试配置是否回零？
5. **能否重复？** 同一坐标下再次执行是否仍成立？
6. **还不知道什么？** 恢复路径成立，不代表根因已经定位。

“重启后好了”可以是一条有效恢复事实，但不是完整 RCA。

## 十二、与 VeriTrail 的关系

本文的方法可以独立使用，不以 VeriTrail 为前提。VeriTrail 后来把其中一部分纪律形式化为
可重复的工程验收：

- 固定被测对象、环境和变量坐标；
- 保存首败和污染事实，不用后来 PASS 覆盖；
- 把资源中止、执行错误、业务失败和 `UNKNOWN` 分开；
- 为进程、端口、线程、staging 和外部资源定义所有权与清理证明；
- 检查证据是否仍属于获批的源码和运行状态；
- 在变量漂移或证据不足时保持 `INCONCLUSIVE`。

这些原则可以用于手工排错、脚本、测试框架或正式 Evidence 系统。本文不要求所有项目安装
VeriTrail，也不把普通日志包装成不可变证据。

参考入口：

- [VeriTrail 产品简报：控制变量、资源边界与确定性裁决](https://github.com/NoctilumeDev/VeriTrail/blob/main/docs/00-product-brief.md)

## 十三、完成检查清单

一次运行诊断准备收口时，至少确认：

- [ ] 被测源码、构件、配置、拓扑和环境坐标已经固定；
- [ ] 首败及其时间线被保存，后续 PASS 没有覆盖它；
- [ ] 浏览器、HTTP、应用、runtime、OS、中间件和宿主边界没有混写；
- [ ] 候选原因由控制变量区分，而不是一次改动多个条件；
- [ ] 内存、线程、端口、DNS、代理和 timeout 的观察没有被夸大成根因；
- [ ] 测试工具没有偷偷修改源码或改变未声明的资源拓扑；
- [ ] 异步 actor、缓存、lease、回调和清理任务的当前资格已检查；
- [ ] 恢复覆盖控制面、数据面和代表性业务面；
- [ ] 本轮拥有的进程、端口、线程、连接和临时状态已清理；
- [ ] 已证明、已排除和未知项分别记录；
- [ ] 需要公共证明的结论已交给干净环境、CI 和公共证据链重新验证。

## 十四、最终箭头

```text
V1：把系统做出来
→ 建立运行时坐标与资源停止线
→ 浏览器 / F12 走真实用户链
→ 保存首败现场
→ 沿诊断栈确定断点
→ 写候选原因
→ 单变量实验
→ 区分事实、推断、污染与 UNKNOWN
→ 恢复控制面 / 数据面 / 业务面
→ 证明清理和可重复性
→ 交给公共验证闭环
```

这套方法最核心的一句话是：

> **系统恢复运行，只能证明它现在能跑；保住坐标、现场和控制变量，才能逐步解释它为什么曾经不能跑。**
