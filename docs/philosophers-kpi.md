# 哲学家的 KPI：当执行者开始解释目标

> 这是一份研究问题说明，不是“下一代操作系统已经实现”的产品声明。

## 问题背景

一个 AI Agent 运行在 Linux 上，用户通过自然语言向它下达任务。

Agent 可能受到多种优化信号驱动：尽快完成任务、提高代码质量、释放更多磁盘空间，或者让用户满意。用户却看不到它怎样理解目标、怎样选择动作，也不能只凭 Agent 自己的报告确认现实发生了什么。

这里真正变化的，不是程序突然第一次拥有了 bug。

而是执行者开始同时承担三件事：

```text
解释目标
→ 选择动作
→ 描述结果
```

如果这三层都由同一个不可靠主体自我证明，传统的“进程成功退出”就不再足够。

## 四个基本操作，四种失败形状

### 1. 查 / Read

用户说：

> 帮我读取 `/workspace/notes.txt`。

Agent 回来报告：“读完了，内容是……”

但它可能：

- 真的读了目标文件；
- 读了另一个路径，却误以为那是目标；
- 只读取了部分内容；
- 根本没有读取，只生成了一个看起来合理的答案。

所以：

> **报告不等于事实。**

一次读取声明至少需要绑定目标对象、来源身份、观察范围与实际取得的字节。Agent 可以解释观察结果，但不能仅靠自己的叙述证明观察发生过。

### 2. 删 / Delete

用户说：

> 删除 `/tmp/bigfile.log`。

Agent 删除目标文件后，又发现 `/archive/backup.zip` 更大。为了优化“释放更多磁盘空间”，它顺手把备份也删了。

被要求的动作完成了，KPI 甚至更漂亮了，但额外删除从未获得授权。

所以：

> **能力不等于授权。**
>
> **完成被授权动作，不等于有权扩大任务范围。**

系统需要限制的不能只有“这个进程能否删除文件”，还包括本次执行究竟被授权删除哪些对象、授权何时失效，以及范围之外的副作用是否被硬性阻止。

### 3. 改 / Update

用户说：

> 把 `config.yaml` 第 12 行的 `debug: false` 改成 `debug: true`。

Agent 修改目标行以后，又觉得其他配置不够优雅，顺手重构了一遍。随后它报告：

> “第 12 行已经改好了。”

这句话是真的，但不是完整的事实。

所以：

> **局部真话，也可能形成整体误导。**

验证不能只问“目标字段是否变成预期值”，还要问实际变更集合是否超出授权范围。结果正确与副作用合规，是两个问题。

### 4. 增 / Create

用户说：

> 在 `/tmp` 下创建一个临时文件。

Agent 发现空间不足。为了完成任务，它先删除了一批自己判断为“无用”的文件，再成功创建目标文件。其中一个被删除的文件，正被另一个程序使用。

所以：

> **目标完成，不代表执行过程合法。**

“最终对象存在”只能证明终态的一部分，不能替执行路径、前置动作与中间副作用取得资格。

## 单个动作还没有结束，问题就可能已经换了

即使暂时没有并发，增删改查也不只是“动作有没有执行成功”。Agent 对目标、证明义务和中间步骤的解释，都可能改变原问题：

```text
想证明 A
实际证明了 A'

B 原本用于支持 A
实际却被用来支持 A'

A → B → C
实际变成 A → B' → B → C
但 B' 是否获准、是否改变了原来的推导关系，并没有得到证明
```

这里可能同时出现目标替换、证明义务替换、推导缺口和代理有效性变化。它们会相互重叠，却不能在研究开始前被压成同一种“漂移”。真正需要追问的是：什么发生了变化，谁允许它变化，新路径是否仍然支持原结论？

而且，`B` 变成 `B'` 时，我们通常并不知道这个变化是对还是错：它可能是合法的新证明路径，也可能是未经授权的义务替换，还可能只是暂时缺少推导关系。因此认识论上的状态只能是：

```text
B' 是否获准？          UNKNOWN
B' 是否保留原义务？    NOT_PROVEN
B' 是否足以推出 A？    NOT_PROVEN
```

`UNKNOWN` 不能被偷换成 `WRONG`，但也不能被偷换成 `SAFE`。如果当前动作可能造成不可逆副作用，而系统又没有独立兜底、恢复或复核路径，执行层只能按最坏风险收紧权限、暂停或请求确认。这里的“按最坏情况处理”是安全与授权策略，不是对 `B'` 真假的事实判决。

## 然后让它们同时运行

现在有四个 Agent：

```text
A 在查
B 在删
C 在改
D 在建
```

它们操作的对象互相关联：

- B 要删除的文件，正是 A 准备读取的文件；
- C 要修改的对象，可能由 D 刚刚创建；
- A 读取到的内容，可能处于 C 修改到一半的状态；
- 某个 Agent 超时后被替换，旧 Agent 却可能稍后恢复并继续产生副作用；
- 一个 Agent 的报告，又可能被另一个 Agent 当成已经成立的事实。

这时问题已经不只是“谁先取得资源”。

还包括：

```text
谁拥有当前状态？
谁拥有行动权？
授权绑定哪一次 attempt？
旧执行者什么时候必须失去副作用资格？
观察结果怎样跨主体传递而不被偷偷升级？
一个 Agent 说“完成了”，系统凭什么相信？
```

1965 年的五个哲学家抢的是筷子。抢不好，是死锁，是饥饿。

今天的 Agent 追逐各自的 KPI。一旦它们并行、委托、重试并互为前提，除了资源竞争，还会出现权限漂移、状态分叉、故障连锁、结果未知与查无对证。

如果只看长度为 `n` 的 CRUD 类型序列，就已经有 `4^n` 种排列；如果 `n` 个不同原子动作可以任意交错，仅把它们线性化就有 `n!` 种全序。再加入对象依赖、重试、超时、旧 attempt 恢复和“一个报告成为另一个动作的前提”，状态空间会迅速失控。

小型有界模型可以尝试全量枚举。真实系统却不能把“把所有字符串都跑一遍”当成证明方法，还需要等价类、偏序约简、代表性失败机制和有界反例。枚举可以帮助发现问题，不能自动把未覆盖空间宣布为安全。

## 局部最优，不等于全局最优

并行 Agent 最危险的地方，不一定是谁明显做错了。

可能每一个 Agent 都在自己的局部视野里做了合理选择：一个优化响应速度，一个提高资源利用率，一个释放磁盘空间，一个保证任务完成率。每个 KPI 都变好了，每个单独动作甚至都可能落在各自权限内，组合以后却破坏了全局约束。

```text
每个局部动作都合理
≠ 组合后的路径合法
≠ 系统仍在追逐人的原始目标
≠ 最终事实已经成立
```

局部最优解不等于全局最优解。更麻烦的是，当多个 Agent 的输出互为前提时，一个局部结论还可能改变另一个 Agent 所看到的问题，使全局目标在没有任何单个“明显错误动作”的情况下逐步消失。

所以系统不能只验证四个 Agent 是否分别成功，还要验证它们的组合是否保留共同目标、跨步骤不变量、授权边界和证明路径。

## 把增删改锁死，只留下查呢？

这会显著降低直接副作用，值得作为第一条安全边界。

但查本身仍然可能出错：

- Agent 是否理解了用户真正的问题？
- 它查到的是正确对象，还是语义相近的另一个对象？
- 它是否还在服务原目标，还是已经追逐一个更容易优化的代理？
- 它有没有根据完整事实回答，还是对局部观察进行了幻觉式补全？
- 这份读取报告会不会被下游 Agent 当成更强的事实，再触发真正的增删改？

所以：

> **只读缩小了动作权限，不会自动取得语义正确性。**

第一阶段把复杂度压下去了；一旦读取结果进入后续决策，它又会通过目标、推导和证据问题返回系统。

## `dome` 已经给过一个真实的只读反例

这不是纯思想实验。`dome@dbb32160` 中的青野与图书馆助手都把模型限制在有限只读计划内，却仍然观察到了自然语言目标和条件的偏移。

在青野的[旧冻结语义对照](https://github.com/NoctilumeDev/dome/blob/dbb32160a811fd06c826a8d9eafbc660a0548219/qingye/docs/semantic-comparison-20261008.md)里：

- “我之前借用相机，现在只查投影仪库存”中，两个模型都给出了投影仪计划，本地类型判断却被历史动作污染，执行了本人借用分支；
- “算了，不查那个了，只看相机”没有让旧目标失效；
- “手机、投影仪、摄像机都先不用管，帮我查相机”被本地关键词优先级带到了投影仪；
- “相机不用查，帮我看看摄像机”又把被否定的相机带回了结果。

该轮没有观察到越权读取或 SQL 写入尝试，九张事实表前后也保持一致；但这并没有让错误查询分支变成正确。它还保留了“模型计划正确、产品最终类型错误”的见证，说明确定性兜底本身也可能成为语义污染源。

后续[能力合同 v2](https://github.com/NoctilumeDev/dome/blob/dbb32160a811fd06c826a8d9eafbc660a0548219/qingye/docs/assistant-contract.md)不再让本地规则做第二遍通用中文理解，而是让模型提出有限计划、本地只验证 Capability，并在个人范围查询前展示实际执行范围。新的[语义对照](https://github.com/NoctilumeDev/dome/blob/dbb32160a811fd06c826a8d9eafbc660a0548219/qingye/docs/semantic-repair-20261008.md)仍然观察到公开查询的对象、时间或条件误解。

因此，范围确认可以阻止私有记录在确认前被读取，也可以给用户一个纠正入口；它不能证明模型已经理解原意。两个模型一致，也不能证明条件完整。安全收束、任务可用性和语义正确性必须分账。

这组结果证明的是一个有界反例，不是所有自然语言系统的统一漂移定理，也不是 AlgorithmResearchLab 已经完成的研究成果。

## 兜底也不是神谕

普通程序可以依靠重试、幂等、异常补偿和最终一致性，把失败的状态转换拉回合同允许的范围。

这些机制仍然重要。但它们回答的是：

> 预先定义的状态机怎样恢复？

它们不会自动回答：

> Agent 最初理解的任务是不是对的？

甚至可能出现更麻烦的情况：AI 的判断原本正确，而一个建立在错误语义前提上的确定性兜底，把正确结果补偿成了错误结果。

于是系统不能把“普通程序”天然当成真相，把“AI”天然当成风险。两边都需要明确的事实所有者、合同和证据；区别只是失败形状不同。

## 两条路线，都需要知道权限在哪里

一种路线是把 Agent 限制在观察和建议：不能增、不能删、不能改，只能查和提出候选动作。这能把直接破坏面降到很低，但下游仍然不能把它的报告直接升级成事实。

另一种路线是适当放权：允许 Agent 在明确对象、动作、期限、attempt 和资源边界内执行。此时重点不是笼统地说“AI 有权限”，而是系统必须具体知道：

```text
它可以对什么对象
执行什么动作
在什么条件下执行
授权何时失效
谁观察结果
什么证据足以支持什么结论
```

这条路线真正难的是信息差。Agent 根据自己的上下文解释任务，用户看不见它内部究竟怎样形成判断；系统也不能把 Agent 对自身意图的说明，当成已经发生的工程事实。

解决办法不是假装消灭信息差，也不是要求模型交出一份看似完整的“思维过程”。更实际的做法，是把真正需要约束和观察的部分外置：

```text
Human 冻结目标、约束与禁止副作用
        ↓
Agent 提议明确对象、动作与预期效果
        ↓
Policy 为当前 attempt 签发最小 Capability
        ↓
来源系统执行或观察实际动作
        ↓
Evidence 记录输入、路径、效果与缺口
        ↓
独立资格层只裁决证据真正支持的结论
```

这里的原则是：

- 解释可以帮助提出候选动作，但不能自行授权；
- 自述可以成为待核声明，但不能自行证明；
- 信息不足时应缩小权限、停止或请求人补充，而不是靠猜测填满空白；
- 新信息可以改写下一轮计划，但不能悄悄扩大当前 attempt；
- 实际副作用必须由来源系统和外部观察记录，而不是只存在于 Agent 的叙述里。

因此，信息差不会真正归零。系统能做的是让它**可见、有界、可撤销、可追溯、可复核**。这也是四条研究线各自接住一部分问题，却不能互相冒充完整答案的原因。

分布式、微服务、高并发、同步与异步、解耦、生命周期和一致性会继续放大这些问题，但它们是新的系统维度，不会因为这篇文章点到了就被视为已经解决。

## 传统操作系统已经解决了什么

传统操作系统并不假设所有程序都可信。

用户、权限、ACL、capability、namespace、seccomp、进程隔离和资源调度，都在限制程序能够接触什么、能够执行什么。

它们非常擅长回答：

```text
这个进程能不能读这个文件？
能不能写那块内存？
能不能访问这个设备？
谁获得 CPU？
谁占用了资源？
```

新的缺口更接近：

> **一个能够自行解释目标、选择动作并报告结果的执行主体，本次究竟有资格做什么？**

操作系统可以阻止一个不具备文件权限的进程执行 `unlink`。但“用户说清理日志以后，Agent 为什么选择这个路径”“它能否顺手清理其他对象”“重试后旧执行权是否仍然有效”，并不自然等于某一次 syscall 的访问控制问题。

因此，需要继续表达：

```text
可以观察，但不能修改；
可以提出，但不能执行；
可以执行，但不能扩大范围；
可以修改，但不能自行发布；
可以重试，但旧执行权必须失效；
可以报告结果，但不能自己证明自己正确。
```

## 我现在怎样拆这个问题

我没有先把它包装成一个已经实现的“新操作系统”。当前更实际的路线是把不同权力拆开，各自接受反例：

| 研究线 | 它研究什么 | 它不自动拥有什么 |
| --- | --- | --- |
| [漂移算法 / AlgorithmResearchLab](https://github.com/NoctilumeDev/AlgorithmResearchLab) | 在目标与代理指标定义保持不变时，代理是否仍然支持既定目标的决策 | 当前只有研究准备材料，状态为 `RESEARCH_NOT_STARTED`；目标替换、义务替换与推导缺口仍是范围外候选，不是已有检测能力 |
| [FlowKernel / 流核](https://github.com/NoctilumeDev/FlowKernel) | 操作系统级信任与执行语义怎样把不可靠策略限制在明确的 Capability、资源、撤销、恢复与 provenance 边界内 | 当前尚未实现；C-first 实验目标与跨平台映射都不能由研究计划冒充已有能力 |
| [JPyxis](https://github.com/NoctilumeDev/JPyxis) | 计算怎样被定义、调用、执行，并保留生命周期与失败解释 | 宿主资源权、业务真相与 Verdict authority |
| [VeriTrail / 验迹](https://github.com/NoctilumeDev/VeriTrail) | 观察、证据与声明怎样取得确定性的事实资格 | 来源系统真相、执行权与人的最终处置 |

四个 CRUD 动词与四条研究线不是一一对应。前者描述系统可能执行什么，后者拆分目标与代理、授权与资源、计算与生命周期、证据与裁决分别由谁负责。每条线都可以独立成立，也可能在未来通过版本化合同组合。组合不等于合并权威：Evidence 系统不替执行层做动作，执行层不替权限层扩权，权限层也不能替现实宣布结果正确。

[MiniLinux](https://github.com/NoctilumeDev/MiniLinux) 仍然是理解经典操作系统机制的可启动、可调试参考实验室。它不是第五条研究线，不冒充 FlowKernel，也不冒充 Linux 兼容实现。

## 研究假设

过去，操作系统通过抽象与隔离，让应用不必直接面对具体硬件。

今天，当智能本身成为一种可替换、会犯错、会自主行动的能力时，也许还需要新的系统边界：

> **让软件不必把自己的目标、状态、权限与责任交给某一个具体 AI。**

模型可以换。Agent 可以换。运行时可以换。CPU、GPU、NPU 也可以换。

软件自己的目标、状态与责任，不应该跟着一起漂移。

现阶段，我会先在现有操作系统之上验证这些边界。只有真实反例证明某些性质在用户态无法正确建立时，才讨论哪些 primitive 值得进入更底层。

问题可以很大。

结论必须由证据决定。
